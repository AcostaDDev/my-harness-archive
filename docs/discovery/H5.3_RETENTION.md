## Política y procedimiento

La política formato 1 selecciona los originales externos `stdout.bin` y
`stderr.bin` de CLI gestionadas por fecha de finalización anterior al corte UTC
exclusivo y tamaño mínimo. El corte es obligatorio; el umbral predeterminado es
1 MiB. Sin configuración ni invocación explícita se conserva todo. Cambiar ambos
valores permite otras políticas locales, sin jobs periódicos ni purga automática.

Solo son elegibles capturas selladas con resultado persistido, intento terminado,
run terminal y job DONE. Se excluyen grupos vivos/desconocidos, locks, trabajo
pendiente/recuperación en el checkout, otros intentos inciertos y referencias
compartidas con evidencia protegida. No se infiere parada por lease. La purga
exige servicio/escritores detenidos, propietarios cerrados y grupos históricos
comprobados muertos, sin señalizarlos. La vista previa identifica exclusiones.

Se conservan contratos, contexto, prompts originales/versiones, snapshots,
permisos/consumos, decisiones, aprobaciones, veredictos, evidencia Git, JUnit,
artefactos de migración, payloads/resultados y eventos con hashes/rangos de streams.
Eliminar un original no cambia aceptación, éxito, exit code ni estado operativo.

Ejemplo de comandos disponibles, con rutas/fecha/hash que debe elegir el operador;
**no ejecutado sobre archivos reales**:

```sh
UV_CACHE_DIR=.local/uv-cache uv run --frozen --offline python -m harness_local.cli logs-preview /ruta/local/state.sqlite3 --artifact-root /ruta/local/captures --before 2026-09-01T00:00:00Z --min-bytes 1048576
UV_CACHE_DIR=.local/uv-cache uv run --frozen --offline python -m harness_local.cli logs-apply /ruta/local/state.sqlite3 --artifact-root /ruta/local/captures --before 2026-09-01T00:00:00Z --min-bytes 1048576 --preview-sha256 HASH_REVISADO --reason 'Política local revisada' --confirmed --writers-stopped
UV_CACHE_DIR=.local/uv-cache uv run --frozen --offline python -m harness_local.cli logs-inspect /ruta/local/state.sqlite3 ID_INTENTO
```

La SQLite y las raíces deben ser canónicas, sin enlaces y fuera de checkouts.
Solo se eliminan rutas conocidas del journal; no se recorre una carpeta buscando
archivos sin referencia. La vista previa JSON contiene política, raíces, originales,
hash/tamaño, elegibilidad/diagnósticos, autorizaciones anteriores, bytes que se
retirarán y evidencias preservadas. Su SHA-256 sella todo ese contenido. El comando
de aplicación vuelve a calcularlo: una vista obsoleta falla sin guardar intenciones.

## Auditoría y recuperación

`BEGIN IMMEDIATE` serializa cada fase frente a escritores de SQLite. Antes del
primer efecto se confirman eventos `log_retention_intent`, con operación, run,
intento/stream/ruta, hash/tamaño exactos, política, hash de preview, motivo y UID
del operador local. También sella un hash del conjunto de referencias (incluidos
rangos y hashes parciales), comprobable después de retirar el original. Los
eventos incrementan la versión/secuencia del run siguiendo
el journal existente; ninguna fila congelada se modifica. Después se comprueba
de nuevo la elegibilidad y se verifican los bytes contra captura y rangos.

La retirada usa descriptores de directorios/fichero con O_NOFOLLOW, archivos
regulares sin enlaces duros, lectura acotada, identidad/metadatos antes y después,
unlink relativo al descriptor y fsync del directorio. Los resultados se registran
como `log_retention_removed`. Una segunda aplicación con preview nueva y sin
candidatos no produce eventos ni otros efectos.

Una caída después de guardar intenciones deja `pending`, tanto si el original
sigue presente como si ya falta. No se concilia automáticamente. Se exige vista
previa nueva y otra aplicación explícita; `log_retention_reconfirmed` conserva su
confirmación. Reutiliza la intención original. Si ya falta, se registra
`observed_removed_bytes=null`: el tamaño retirado del conjunto se conoce por su
referencia, pero no se inventa una retirada observada durante la recuperación.
Los totales observados y retirados se presentan por separado.

Si aparece contenido ajeno tras una intención, no se elimina. Para conciliar,
el operador debe recuperar manualmente el original sellado y revisar otra vista
previa. No existe abandono de intención pendiente; mientras tanto se bloquea
la publicación de backups. No se restauran ni descartan bytes automáticamente.

## Consulta y backup

`logs-inspect` y GET
`/api/managed/runs/{run_id}/attempts/{attempt_id}/logs` distinguen:

- `retained`: original comprobado contra hash/tamaño/rangos;
- `purged`: retirada autorizada y registrada, con su procedencia;
- `pending`: intención duradera que requiere conciliación;
- `missing`: pérdida sin retirada autorizada;
- `unverified`: corrupción, enlaces, errores o límites.

La ruta comprueba pertenencia del intento al run y conserva Host de loopback.
La UI ofrece «Comprobar originales de logs» por intento, sin releer grandes logs
en cada sondeo. No entrega cuerpos, ni sirve una sustitución como versión sellada.
Un intento sin transporte CLI devuelve lista vacía. React muestra datos como texto.

El bundle H5.2 formato 1 añade `absent_purged`, contrastado con intención/resultado
en SQLite y las referencias exactas. Toda referencia debe estar copiada, ser
opcional o estar retirada con auditoría válida. Una pérdida, corrupción, intención
pendiente, prueba incompleta o original purgado reaparecido impide publicar copia.
Backup y restauración conservan evidencias restantes y eventos completos. Los
bundles anteriores sin ese campo siguen siendo válidos si no hay purgas; no se
modifican las copias existentes ni se reescriben rutas históricas. La consulta de
logs retenidos en una restauración usa el mapeo verificado, nunca sus originales.
La marca persistente de consulta impide aplicar retención a copias/restauraciones.

## Verificación y límites

Pruebas sintéticas en `tests/product/test_retention.py`: política/determinismo,
preservación de filas/historial/prompts/hashes, confirmaciones obsoletas, intentos
activos/inciertos, locks, propietarios/grupos, pérdidas/corrupción/enlaces/FIFO,
límites, rangos, referencia compartida, caídas antes/después de unlink,
reconfirmación, escritura concurrente, CLI/HTTP y backup/restauración nuevo/antiguo.
Se comprueba que otra versión del fichero no se adopta ni elimina. Regresión H5.2,
suite completa, checks ligeros/Node y compilación frontend en STATE.

Límites: 256 MiB por fichero/SQLite, 2 GiB por aplicación y 10.000 referencias;
los manifiestos H5.2 siguen acotados a 4 MiB. La exclusión externa es cooperativa:
no existe una transacción atómica entre SQLite y unlink ni defensa frente a
manipulación del propietario o sustituciones después del último stat. El
servicio debe permanecer detenido también entre las dos transacciones.
No hay rotación, límite nuevo de captura durante ejecución, GC de temporales,
purga legacy/JUnit/payloads SQLite, benchmark, proveedores ni navegador en vivo.
Solo se retiraron capturas sintéticas temporales. H5.4 queda pendiente.
