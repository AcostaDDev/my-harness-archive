## Frontera e integración

`adapters/cli_agents.py` aporta `CLIConfig` y `CLIProcessAdapter`. Codex ejecuta
planificación/revisión mediante `exec`; Claude Code ejecuta implementación en
modo print. El núcleo conserva sus puertos de biblioteca estándar. El supervisor
H2.2 recibe el adaptador por su factory y enlaza un journal de procesos al job
reclamado. No hay autoarranque, endpoint/comando gestionado ni conexión con la UI.
Las validaciones y captura de contenido siguen siendo otros puertos; esta entrega
no implementa comandos de proyecto reales ni captura Git H2.4.

Se exige una instancia nueva del adaptador por job, ambas CLI configuradas y
SQLite/artefactos fuera del checkout. `frozen_versions()` aporta versión del
adaptador, versiones CLI declaradas y hash de configuración. Se guardan al
encolar junto a H2.2; un cambio de configuración antes de ejecutar bloquea el job.
`preflight()` comprueba versión exacta y flags requeridos en help, registra salida
de versión/hash de help y no consulta login, cuota, modelos disponibles o secretos.
La disponibilidad del binario no acredita acceso a un modelo ni autenticación.

La corrección `cli-2` cambia el argv y la declaración de retries internos. Jobs
congelados `cli-1` no ejecutan automáticamente esta versión; se rechazan antes de
lanzar por comparación de versión. No se reescribe historial ni hay migración nueva.

## Solicitud explícita y permisos

- Argv separado, ejecutable absoluto, cwd canónico, entorno completo aportado y
  timeout positivo/finito. No hereda variables automáticamente ni usa shell.
- Modelo/esfuerzo explícitos de la solicitud congelada; el esfuerzo de Claude
  admite únicamente los valores declarados por su help. No convierte esfuerzos
  entre proveedores ni sustituye una selección que falle.
- Codex: `--ephemeral`, sin resume/fork; read-only, approval never, configuración
  de usuario/rules ignoradas, proveedor OpenAI explícito, web search deshabilitada.
- Claude: UUID nuevo de intento y `--no-session-persistence`, sin continue/resume,
  fallback o bypass. `dontAsk`/permission prompts none; herramientas disponibles y
  preautorizadas declaradas, vacías por defecto. MCP externos, hooks y fuentes de
  settings locales se deshabilitan por flags/configuración de esta invocación.
- El prompt efectivo añade formato JSON y selección permitida para Codex al
  prompt del motor. Se conserva en `prompt.txt` con hash/ruta antes de lanzar.
  Spec persistida contiene argv, cwd, timeout, permisos, proveedor/versiones y
  claves/hash del entorno; no vuelca valores de credenciales en eventos.

Las CLI administran sus propias suscripciones y autenticación. No se extraen ni
transfieren tokens, no se implementa login propio ni fallback a API de pago.
Las herramientas de Claude no constituyen una sandbox de archivos/red del SO.
El contrato/política del motor tampoco impide físicamente escrituras de una CLI:
no se afirma aislamiento total ni autorizaciones web vivas. Conceder herramientas
requiere configurar un intento posterior explícito.

El adaptador hace una sola invocación de agente por intento. `cli-1` solicitaba
cero retries HTTP/stream mediante overrides reservados rechazados por Codex 0.162.1.
`cli-2` los elimina, conserva `model_provider="openai"` y declara
`built-in-defaults/unknown` en capabilities y spec persistida. La referencia
documenta controles por proveedor personalizado y no se encontró una opción
compatible de cero para el integrado; no se cambia el proveedor para conseguirla.
Claude no expone control equivalente
verificado. Los retries internos, cuota y límites de suscripción **no han sido
caracterizados con cuenta real**; no se promete una sola petición de inferencia
por proceso. No se pasa `--fallback-model`, no se cambian modelos ni se relanza
una CLI ante error. IDs reservados y configuración de retries documentados en la
[referencia oficial](https://learn.chatgpt.com/docs/config-file/config-reference).

## Streams y evidencia

`adapters/streams.py` parsea JSONL incremental UTF-8 estricto. Conserva eventos
futuros y campos desconocidos; distingue ausencia/null/cero. Modelo/esfuerzo,
IDs, uso, duración/coste y denegaciones se registran únicamente si aparecen.
Los modelos de mensajes se conservan separados de la selección solicitada.
La duración de pared medida por el supervisor tiene su propio campo, separado
de duración reportada por el proveedor.

`stdout.bin` y `stderr.bin` conservan bytes exactos, incluidos UTF-8 inválido y
cola cortada. Cada bloque se escribe/flush/fsync antes de publicar rango/tamaño/
SHA-256 en SQLite; puede quedar un sufijo sin evento si falla la escritura SQL.
Spec/identidad conservan dónde encontrarlo tras una caída. Al terminar se guardan
referencias con hash/tamaño finales. Eventos originales hasta 16 KiB se conservan
en el feed; los mayores se referencian por rango/hash del stdout, evitando blobs
grandes en SQLite. Límite explícito de 4 MiB por registro JSONL; el exceso detiene
el proceso como inválido y conserva los bytes capturados. No hay retención/GC.

Codex requiere terminal `turn.completed`/`turn.failed`; el payload proviene del
último `agent_message` completado. Claude requiere `result` conocido, `is_error`
booleano y subtype; acepta objeto `structured_output` o JSON objeto en `result`.
Un mensaje del agente por sí solo no es fin. Un resultado completo exige un único
terminal conocido, exit cero, JSON objeto válido y ausencia de errores/cola.

| Estado del resultado | Significado |
|---|---|
| complete | Stream y payload completos; el motor aún valida su contrato |
| partial | EOF sin terminal o cola JSON/UTF-8 incompleta |
| invalid | JSON/envelope/payload inválido, final desconocido o terminal duplicado |
| failed | Error conocido/cuota sintética, exit no cero, hijo vivo tras el líder o stdin fallido |
| timeout | Plazo agotado; se solicita parada del grupo |
| cancelled | Cancelación explícita; se solicita parada del grupo |

Los resultados CLI usan historial codec formato 2; el lector conserva soporte de
formato 1, sus defaults ausentes y resultados anteriores sin reescribirlos.
Resultado y estado del intento se conservan en el checkpoint atómico H2.2;
`complete` no certifica aceptación/commit. Error/partial/invalid/timeout/cancelled
interrumpen el motor sin llamada a reviewer ni fallback. Fallo del journal se
propaga y deja recuperación pendiente, con el intento y evidencias inciertos.

Fuentes contrastadas con el help local: [Codex no interactivo](https://learn.chatgpt.com/docs/non-interactive-mode)
y [Claude print/streaming](https://code.claude.com/docs/en/headless).
Las pruebas siguientes son sintéticas, no ensayos de estos servicios.

## Lanzamiento, cancelación y recuperación

Migración explícita `0005_cli_processes`: `managed_processes` y propietario/
cierre del ámbito en `managed_jobs`. Upgrade/downgrade a 0004 conserva los datos
previos H2.2; el downgrade elimina la evidencia de procesos H2.3. No convierte
historial formato 2 al formato que entiende un binario antiguo H2.2. Migrar con el
servicio detenido, sin escritores pendientes, antes de arrancar esta versión.

El supervisor registra host/PID y token del job antes de lanzar efectos. Cada
intento tiene una intención única, spec y un grupo POSIX nuevo. Un proceso gate
espera un byte por pipe independiente; solo después de persistir PID/PGID el
padre envía GO. Si el padre cae antes, EOF cierra el gate sin ejecutar el objetivo.
Si falla la persistencia, se detiene el grupo y no se envía GO. Cerrar el ámbito
prohíbe nuevas intenciones/identidades de procesos, incluso con un gate pendiente.

`cancel(attempt_id)` marca una solicitud; el bucle propietario envía TERM, espera
un plazo breve y escala a KILL al grupo completo. Drena stdout/stderr con plazo
acotado y reap del líder. Si el líder termina dejando hijos vivos, se detiene el
grupo y se registra fallo. Si su muerte no puede acreditarse, no se finaliza el
job: permanece bloqueado en recuperación.

La reconciliación H2.2 sigue siendo una acción explícita sobre job/token/versión.
`confirm_stopped` ahora comprueba propietario y todos los grupos persistidos:
si el ámbito sigue abierto, exige propietario ausente; además exige grupos
ausentes. Usa señal 0; permiso denegado, host distinto o PID/grupo vivo son
incertidumbre y rechazan liberación. La caducidad del lease y la muerte del
supervisor nunca bastan para descartar sus hijos. Se conservan intentos de
resultado desconocido y presupuesto, sin repetir efectos.

Un PID reutilizado sigue siendo «vivo», conservadoramente. No se envían señales
a identidades recuperadas: sin un handle vivo no se acredita que sean el proceso
original. Puede ser necesaria una intervención local para detener al escritor;
la confirmación posterior comprueba ausencia. No depende de ps. Señal 0 limitada
por sandbox mantiene el lock, no se interpreta como muerte.

Garantía cooperativa local sobre una base y grupos que no escapen con setsid u
otros mecanismos. No es supervisión hostil de todo el árbol, aislamiento de SO,
protección contra escritores externos/otra base/raíces solapadas ni exactamente
una vez. macOS POSIX comprobado; otros sistemas y carga sostenida no ensayados.
