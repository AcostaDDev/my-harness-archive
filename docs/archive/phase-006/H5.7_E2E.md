## Recorridos añadidos

`tests/product/test_e2e_offline.py` conecta API, sesión real, supervisor opt-in,
SQLite y Git temporales. Solo los puertos de agentes y comandos son falsos.
Las llamadas HTTP usan TestClient en proceso; cada reinicio crea otro lifespan.

| Recorrido | Resultado comprobado |
|---|---|
| Sesión → ejecutar → cerrar sesión → reiniciar → editar externamente → commit → revalidar | 401 sin efectos; cookie anterior inválida; mismo job/eventos; commit obsoleto rechazado; nueva evidencia antes de un único commit; checkout principal intacto |
| Ejecutar → fallo inyectado de persistencia del revisor → reiniciar → recuperar | Cuarentena/lock y eventos conservados; ni reinicio ni confirmación relanzan; token incorrecto rechazado; revalidación explícita añade revisor nuevo y conserva el incierto como INTERRUPTED; ejecutor no repetido |
| Parada → solicitar permiso → denegar → reiniciar → reintentar → sustituir/conceder → reintentar | Denegación impide invocación; decisión antigua rechazada; conceder no ejecuta; concesión once consumida por el intento exacto; historial y presupuesto conservados |
| Importar/activar → ejecutar con tests fallidos → reiniciar → revalidar → commit | Importación repetida idempotente; ACCEPT no supera tests fallidos; commit bloqueado; ciclo fallido conservado después de nueva validación |
| Importar/activar → ejecutar con review BLOCKED → reiniciar → revalidar → commit | Review bloqueante impide commit; revalidar no repite ejecutor; histórico legacy sigue consultable |
| Crear → preview/confirmar → reiniciar → primera tarea → commit | Sin confirmar no escribe; bootstrap no invoca agentes; doble confirmación mantiene job; primera tarea documental separada; dos commits (raíz y tarea); fase sigue ACTIVE |

La fixture legacy declara en su `.gitignore` el marcador gestionado antes de
activar (igual que la demo H2). No se altera silenciosamente el alcance para
aceptar ese archivo operativo en un commit de tarea. La fixture de permisos
congela presupuesto de tres revisiones para permitir los dos reintentos del
recorrido; una denegación no reinicia el presupuesto.

El cliente Node añade el recorrido de respuesta perdida tras admisión, 401,
nueva sesión y reenvío humano: mismo cuerpo/ruta/clave y un solo job en servidor
simulado. No monta React ni demuestra interacción visual; las guardias reales y
la idempotencia real se comprueban en Python/HTTP.

## Instalación aislada

`scripts/check_distribution.py` amplía el verificador existente: wheel instalado
en venv nuevo con 18 dependencias fijadas y hashes, cwd temporal y PATH sin Node
ni proveedores. Solo añade Git al PATH mediante enlace al ejecutable local.
Copia `tests/fixtures/e2e/installed_config.py` junto a la instalación temporal;
ese módulo autónomo registra un destino vacío y puertos falsos explícitos.
PYTHONPATH solo señala esa carpeta temporal durante el flujo gestionado, nunca
el checkout de desarrollo. No incluye factories sintéticas en el wheel.

Por HTTP loopback real: login, preview, rechazo sin confirmación, bootstrap,
reinicio, primera tarea, ACCEPTANCE_READY, commit, doble envío, otro reinicio y
repetición explícita conservando identidad. Auditoría externa acredita exactamente
un ejecutor y un revisor falsos. Se conservan también los checks H5.5/H5.6 de
assets, simulación, sesión, errores de configuración/esquema y cierre.

Con todos los servidores detenidos: backup-create/verify/restore por CLI. Se
mueve el checkout sintético original fuera de su ruta antes de abrir la copia.
La restauración mantiene historial, commit, intentos y eventos exactos por HTTP,
ignora la factory ambiental inválida, deshabilita supervisor y rechaza mutaciones
409. No invoca puertos ni requiere que exista el Git original. No respalda Git.
Los tests existentes de backup comprueban además jobs pendientes/inciertos y
locks sin reactivación.


- Seis recorridos Python nuevos correctos; suite completa: **771 pruebas y
  121 subtests**, incluidos migraciones/OpenAPI. Aviso Starlette/HTTPX conocido.
- **6 pruebas Node y 12 checks ligeros** correctos.
- Build offline de sdist/wheel, TypeScript y Vite correctos; verificador instalado
  con flujo gestionado y restauración correcto. Sin publicar ni push.
- UI: Chrome intentó `http://127.0.0.1:8027` sobre fixture temporal y respondió
  `net::ERR_BLOCKED_BY_CLIENT` antes de mostrar la aplicación. **No hay QA visual
  ni confirmaciones por clic acreditadas en H5.7**. No se eludió el bloqueo.
  El servidor Uvicorn se detuvo limpiamente; su clave efímera se retiró. Bind/TERM
  necesitaron permisos fuera del sandbox. Las pruebas HTTP no se presentan como UI.

## Límites y cierre del alcance

Fakes no acreditan modelos, autenticación CLI, consumo, retries internos ni
permisos efectivos del proveedor. Recuperación inyectada de la nueva suite no
es una caída de proceso; esa frontera se conserva en los tests H2.3 existentes.
La plantilla crea documentación, no una aplicación ni dependencias del stack.
Sin integración de ramas, cierre inferido de fases, reactivación de restauraciones,
publicación, benchmark, otras plataformas ni cambios globales. Solo datos
sintéticos; no se ejecutó ReferenceProject ni el harness para desarrollar el repositorio.

paso es revisar el cierre del hito 5 y acordar con el usuario el próximo alcance;
no se inicia implementación nueva ni smoke. D033.8 sigue exigiendo autorización
