## Declaración y captura

`ProjectProfile.junit_reports` contiene hasta ocho `JUnitDeclaration`, cada una con
un `Command` exacto (argv, cwd, entorno y timeout), una ruta relativa al **checkout**
y una descripción de la cobertura de tests. Es selección declarada por el servidor,
no porcentaje medido de cobertura de código ni permisos de ejecución. No se admiten
rutas aportadas por HTTP. Comandos adicionales del contrato solo importan el reporte
si coinciden exactamente con la declaración congelada; comandos no seleccionados
no producen casos inferidos.

Ejemplo de configuración en un perfil confiable:

```python
from harness_local.core.engine.context import Command, JUnitDeclaration, ProjectProfile

tests = Command(("test-runner", "check"), timeout_seconds=120)
profile = ProjectProfile(
    "example", validations=(tests,),
    junit_reports=(JUnitDeclaration(tests, ".local/junit.xml", "Tests unitarios de app; sin cobertura de código"),),
)
```

El runner configurado debe generar el archivo declarado y el proyecto debe ignorar
sus artefactos de validación. No se añade un runner de comandos de producto ni se
ejecuta un comando para importar. `typescript-web` declara `.local/junit.xml` para
`npm run test`; la fixture mantiene TAP en stdout y usa el reporter JUnit de Node
en paralelo, sin dependencias nuevas. ReferenceProject conserva su configuración sin
inventar un reporte que sus comandos actuales no generan.

Antes y después del comando se observa el archivo mediante descriptores y
`O_NOFOLLOW` en todos los componentes; solo archivo regular sin enlaces duros,
fuera de `.git`, hasta 2 MiB. Se rechazan symlinks, FIFO, directorios, cambios
durante lectura, rutas externas y errores locales. Nunca se borra un reporte
anterior. Archivo nuevo → `created`; firma de archivo/hash distinta → `changed`;
sin cambio → `stale/unchanged`; observación previa no disponible → `unknown`.
Es evidencia de cambio local, no una certificación de que el comando produjo
el archivo frente a otro escritor concurrente.

## Original, casos y aceptación

Los bytes completos, también de XML inválido o truncado dentro del límite, quedan
en base64 con SHA-256 y tamaño en el historial SQLite del run (codec 6). No se
sobrescriben ciclos anteriores. Formatos 1–5 siguen legibles; perfiles e historiales
sin reportes conservan su forma anterior. Esquema `0013_bootstrap`, sin migración.
El detalle enlaza run, ciclo, `command_id` de los eventos, último intento ejecutor
observado y evidencia Git completa. Revalidar crea un comando/ciclo nuevo y conserva
la procedencia del ejecutor anterior. Un check de fase conserva los reportes en su
run; su intento ejecutor es null porque ese flujo no tiene ejecutor.

El parser de biblioteca estándar acepta `testsuite` y `testsuites`, suites anidadas
y casos directamente bajo ambos contenedores. Rechaza DTD, declaraciones de
entidades y entidades externas, incluso con codificación UTF-16; no interpreta
XInclude, rutas `file`, comandos ni contenido de los errores. Límites: 64 niveles,
30.000 elementos, 2.000 casos. Una estructura incompatible o un límite del parser
conserva el original y diagnostica sin atribuir casos. XML truncado/malformado
conserva únicamente casos cerrados observados y marca el reporte parcial.

Por caso: nombre, classname, id reportado, jerarquía de suites, resultado,
duración, mensaje/tipo/texto de fallo. El identificador interno estable es SHA-256
de la identidad observada y el ordinal entre duplicados; no se presenta como id
aportado por el framework. Ausencias permanecen null o jerarquía vacía; cero es
cero. Ausencia de nombre, estados desconocidos o marcadores contradictorios no
fabrican éxito. Totales declarados incoherentes y duraciones inválidas producen
diagnóstico. No se rellenan casos a partir de contadores de suite ni se suman
duraciones individuales como tiempo real de una ejecución paralela.

`exit_code`, stdout/stderr, timeout, error y duración del comando se conservan
intactos. Un reporte nunca acredita éxito de un comando fallido ni aceptación por
sí solo. Fallos/errors de casos en un reporte nuevo observado añaden una puerta
determinista que impide ACCEPT/READY, también si el comando devolvió 0. Reporte
ausente, inválido, parcial sin fallos observados o anterior no fabrica éxitos ni
un resultado de comando distinto; la puerta existente del comando sigue siendo
necesaria. Review, política y contenido exacto siguen obligatorios. Cambiar código
después de revisar impide el commit; alterar/eliminar el XML ignorado después de
capturarlo no modifica la evidencia histórica.

## Consulta

La vista habitual de cada ciclo muestra resúmenes y procedencia. Casos y original
se consultan desde SQLite, sin volver a leer el checkout:

- `GET /api/managed/runs/{id}/cycles/{cycle}/validations/{entry}/reports/{report}`:
  casos con `offset`, `limit` de 1 a 100, `next_offset`, resumen, comando/intento y
  evidencia validada.
- La misma ruta con `/original`: descarga binaria del XML exacto, comprobando su
  hash/tamaño; `attachment`, `nosniff` y ETag SHA-256. No sirve XML como página activa.

Guardia gestionada de loopback conservada. La UI muestra comandos, cobertura,
estado/diagnósticos, descarga y tabla paginada; distingue datos ausentes y duraciones
de comando/test. React renderiza errores como texto. Los prompts nunca incluyen
base64 del original; la revisión de tarea recibe el detalle estructurado y la de
fase recibe su resumen. No se añaden endpoints de escritura para reportes.

- Rutas externas/Git, symlinks de archivo/directorio, enlaces duros, FIFO,
  directorios, tamaño excedido y sustitución durante captura; bytes externos intactos.
- Reporte anterior/nuevo/reescrito idéntico, comando exacto, snapshot congelado,
  codec antiguo/nuevo, comandos fallidos, review inválida, fallos JUnit con exit 0,
  revalidación, check de fase y commit exacto/invalidez ante código cambiado.
- Persistencia/reinicio, paginación HTTP sin duplicados, descarga después de
  editar/eliminar el origen, guardia HTTP y ausencia de originales/casos en sondeo.
- Chrome sobre UI compilada y Git/SQLite temporales, sin supervisor activo:
  resultados, cero frente a duración ausente, errores escapados, cobertura/hash,
  enlace de descarga y commit deshabilitado. Sin errores de consola.

Exclusión frente a escritores externos cooperativa. No se conserva un archivo por
encima del límite ni se importa XML desde reportes legacy. No hay lcov, medición de
cobertura de código, retención/GC, compresión/blobs externos ni benchmark de
historiales grandes. Una caída antes del checkpoint de validación puede dejar solo
los eventos del comando; recuperar exige revalidar explícitamente, sin atribuir
un XML existente a la ejecución caída. Sin proveedores, smokes, SDK, cambios de
autenticación o migración de la SQLite de trabajo.

[Node test reporters](https://nodejs.org/download/release/latest-jod/docs/api/test.html).
