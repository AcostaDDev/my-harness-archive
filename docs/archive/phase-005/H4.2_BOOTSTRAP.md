## Recorrido implementado

El servidor registra una carpeta **existente y vacía** como `ManagedProject` con
`bootstrap_enabled=True`. El perfil, modelos/esfuerzos, versiones y autoridad de
permisos siguen siendo configuración explícita del servidor. La API recibe solo
el identificador del proyecto, nunca una ruta ni un comando del cliente. Sin ese
opt-in no puede crear documentos. Se requiere una `commit_factory` con
`GitWorkspace`; cargar la configuración no crea repositorios ni llama agentes.

1. El usuario introduce problema, usuarios, funciones mínimas, restricciones y
   objetivo de entrega. Cada campo se acota a 4000 caracteres y no admite NUL.
2. Puede solicitar una propuesta Codex de requisitos, alternativas con sus costes
   y decisiones pendientes. Es una acción explícita e independiente. Usa el rol
   `bootstrap`, una sesión nueva de solo lectura y la selección del planificador
   del servidor. El brief y `bootstrap-project` renderizado/versionado quedan
   congelados al encolar. Fallos o salidas inválidas no provocan fallback/reintento.
3. El usuario registra alcance, arquitectura y exclusiones. Las recomendaciones
   del agente no rellenan ni aceptan estos campos automáticamente. Puede crear con
   decisiones propias sin invocar al agente.
4. El preview ofrece los seis archivos completos, hashes, plantilla, primera fase,
   contrato de primera tarea, perfil/política, selecciones y comandos declarados.
   Git se comprueba en lectura; no se instalan dependencias ni ejecuta preparación.
5. Confirmar brief/decisiones/preview con motivo y `Idempotency-Key` encola el
   bootstrap. La petición HTTP no escribe el checkout. Tras verificar el commit,
   el job crea y adopta atómicamente en SQLite la fase `P001`, activa y versionada,
   con `P001-T001` pendiente y sus documentos por hash.
6. «Encolar primera tarea» es otra acción explícita del flujo normal de tareas.
   Su contrato documental es determinista; siguen ejecución, validaciones del
   perfil, revisión independiente y commit H2.4 propio. La UI muestra su estado
   persistido y deshabilita ese botón si ya existe un run de la primera tarea.

## Plantilla mantenida

`core/engine/templates/bootstrap-foundation.json` identifica `project-foundation`
versión 1 con SHA-256 de su recurso. Es una plantilla de fundamentos documentales,
independiente del stack. No introduce un segundo perfil ni genera una aplicación
completa. Sus documentos son:

- `README.md`: estado de la base documental y referencias;
- `docs/BRIEF.md`: brief aceptado;
- `docs/DECISIONS.md`: decisiones explícitas;
- `docs/PROJECT_PROFILE.md`: perfil/política declarados y procedencia de plantilla;
- las rutas `state_file` y `next_steps_file` del contexto del servidor.

Las rutas canónicas deben ser distintas, sin solapamientos como archivo/directorio
ni metadatos Git, y respetar la política de rutas protegidas/sensibles del perfil.
El texto libre se serializa como datos JSON escapados: no puede inyectar headings,
fences, contratos, HTML ni marcadores gestionados. No se interpretan globs,
comandos o selecciones escritos en el brief.

La primera tarea solo permite `docs/DELIVERY_CHECKLIST.md`: concretar usuario,
entrada, resultado esperado y caso de error; mapear cada función mínima aceptada a
una comprobación observable; respetar restricciones/alcance sin decisiones nuevas.
Tiene criterios y validación explícitos, con una selección de ejecutor permitida
por la política. No empieza a implementar el producto desde un brief incompleto.
La plantilla documental se versiona con el paquete; el prompt de descubrimiento
se edita mediante H3.1. Son recursos distintos.

## Autoridad, Git y recuperación

Migración `0013_bootstrap`: `project_bootstraps`, único por raíz y run, guarda el
preview, bytes, decisión/auditoría, intención, resultado y vínculo a la fase.
No cambia el codec ni las filas anteriores. Bajar de revisión con bootstraps o
runs de descubrimiento se rechaza para conservar el historial.

Los dos flujos son runs/jobs existentes (`bootstrap_discovery` / `bootstrap`) con
el lock por checkout, lease, propietario, heartbeat, cuarentena y confirmación de
escritor detenido existentes. No hay hilo/cola de bootstrap adicional. El
resultado de descubrimiento vive en los eventos y sus intentos conservan el
prompt/permisos/resultados originales. Una caída lo deja `UNKNOWN` después de la
confirmación; solicitar otra propuesta exige una acción propia.

La intención del bootstrap fija árbol, mensaje, identidad, fecha, id del commit
raíz y hash de preview antes de escribir. El sellado usa un repositorio temporal
fuera del destino. Se reutilizan el entorno Git aislado, captura completa e
índices temporales H2.4. Un commit raíz sin padre usa una intención propia, no
fabrica una aceptación de tarea ni una fila `managed_commits`. La creación está
revisada por la confirmación humana del preview.

El adaptador crea exclusivamente archivos ausentes; los presentes deben coincidir
con los bytes/modos sellados. `.git/harness-bootstrap.json` acredita la operación
propia y permite completar un init interrumpido. HEAD y referencias deben estar
vacíos o apuntar al commit esperado en `main`; el índice debe estar vacío o ser el
árbol sellado. CAS crea la referencia y concilia el mismo commit. Un índice ajeno
se observa mediante copia temporal y queda byte a byte intacto ante rechazo.

Una caída conserva la operación/intención. Después de confirmar el escritor
anterior detenido, la UI muestra el preview original para reconfirmar y conciliar
con versión vigente. Se reutilizan operación, run y commit; solo el job de
conciliación es nuevo. Nuevas tareas/fases se bloquean mientras el bootstrap no
termina. La fase, definición/base documental y resultado se adoptan junto al fin
del job; una caída en esa transacción revierte la adopción, conservando el commit
para conciliar. No se restaura ni descarta un byte ajeno.

Una carpeta no vacía (incluidos archivos ocultos, directorios o enlaces) se desvía
al flujo de importación existente. También una carpeta vacía dentro de otro Git.
Si cambia después del preview o del encolado, se rechaza sin sobrescribir. La
identidad local del directorio detecta su reemplazo. El bootstrap no certifica que
cualquier repositorio ajeno sea importable: las puertas H1/H2.5 deciden eso.

## Entradas API/UI

Bajo Host/Origin de loopback y `X-Harness-Local: 1` en mutaciones:

- `GET /api/managed/projects/{id}/bootstrap`: capacidad, importación, operación,
  primera tarea y última propuesta;
- `POST …/bootstrap/discovery`: brief y confirmación → job de solo lectura;
- `POST …/bootstrap/preview`: brief y decisiones → preview sin efectos en destino;
- `POST …/bootstrap`: hash exacto, motivo y confirmación → job de creación o
  conciliación con operación/versión observadas.

OpenAPI/tipos generados. Ninguna ruta anterior cambia; solo se añaden los dos
`purpose` a los esquemas de runs. El transporte `cli-4` conserva sus opciones para
roles anteriores y añade el rol Codex `bootstrap` con el mismo sandbox read-only.
No se certifica aquí su ejecución con una CLI real.

## Límites

No se migró la SQLite de trabajo del usuario. Sin CLI real, smokes, login,
consumo de proveedores, red externa, configuración global, ReferenceProject, colaboración
automática, harness de desarrollo ni push. No instala stacks, prepara entornos ni
verifica herramientas de validación externas durante bootstrap; sus declaraciones
se muestran y el flujo normal comprueba las que corresponden al ejecutar tareas.

La exclusión frente a escritores externos es cooperativa, sin atomicidad conjunta
del conjunto de archivos ni sandbox físico. Si la marca de propiedad Git falta o
está dañada, o el init tiene metadatos ajenos, la recuperación es manual. No hay
abandono/limpieza automática de un bootstrap ambiguo, selector HTTP de carpetas,
registro HTTP de proyectos ni varios packs de plantillas. H4.3 queda siguiente,
sin iniciarse. Los consentimientos de smokes siguen agotados.
