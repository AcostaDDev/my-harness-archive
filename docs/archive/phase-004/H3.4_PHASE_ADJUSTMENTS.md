## Guardia H0/H1

La guardia de D028 pasa a `api/security.py` y se aplica también a las mutaciones
H0/H1: `POST /api/simulations` y `PUT /api/legacy/projects/{id}/observation`. Con
ella se exige un Host de loopback. Si el navegador envía Origin, también debe ser
de loopback. Además se exige `X-Harness-Local: 1`. La guardia se ejecuta antes de
buscar el proyecto, así que una petición ajena recibe 403 y nunca un 404 que
revele qué existe.

Las lecturas H0/H1, incluido el SSE legacy, no aplican la guardia. Sigue faltando
la sesión local frente a otros usuarios del sistema operativo (hito 5). En el
cliente, `request` añade la cabecera a cualquier método que no sea seguro, y la
observación usa `api.setObservation`. La cuarta prueba Node verifica ambos casos.

## Lote desatendido con commit

`authorize_batch(..., chain_commits=True, text=...)` crea una autorización con un
alcance explícito. Ese alcance congela:

- las tareas;
- el texto del plan y su hash;
- el hash de la definición;
- el contexto y las versiones del proyecto.

La proyección oculta el texto, el contexto y las versiones, y muestra
`plan_sha256`. Sin `chain_commits` el lote sigue siendo el manual de H3.3: solo
avanza con `batch/next` y no confirma commits. Un lote desatendido rechaza
`batch/next`.

El supervisor llama a `advance_batches` antes de cada `claim`. Para cada lote
desatendido vigente da como máximo un paso. Cada paso se calcula a partir del
estado y se ejecuta en una transacción con la mutación de la cola.

1. Comprueba primero las condiciones de parada:
   - autorización caducada → `EXPIRED`;
   - definición cambiada → `INVALIDATED`;
   - preguntas pendientes o fase no `ACTIVE` → `STOPPED`;
   - algún job del checkout en `RECOVERY_REQUIRED` → `STOPPED`;
   - un job en cola o activo → esperar.
2. Recorre las tareas en orden y salta las que ya tienen una aceptación `COMMITTED`.
3. Si una tarea no tiene un run de este lote, encola el `start` con la clave
   `batch:{auth}:start:{tarea}`. Si encuentra un run iniciado fuera del lote,
   se detiene: el lote no adopta runs ajenos.
4. Si el run está en `acceptance_ready` y es elegible, encola el commit H2.4 con la
   clave `batch:{auth}:commit:{run}`. El commit de contenido exacto vuelve a capturar
   el contenido y se invalida si cambió.
5. Si el run terminó sin una aceptación elegible, o si su commit no llegó a
   `COMMITTED` (por evidencia invalidada o incierta), el lote pasa a `STOPPED`
   con el motivo.
6. Cuando todas las tareas tienen commit, la autorización pasa a `COMPLETED`.

El lote nunca comprueba ni cierra la fase. Si el usuario lanza un check, la fase
deja de estar `ACTIVE` y el lote se detiene. Revocar el lote impide encadenar más
trabajo, pero un job que ya estaba encolado termina igualmente.

Como el estado vive en SQLite y las claves son deterministas, un reinicio no
duplica trabajo. Si una caída deja un job en cuarentena, el lote se detiene: la
recuperación H2 sigue siendo explícita y nunca se repite un efecto incierto. Para
continuar hay que crear otra autorización. Una tarea con un run previo sin commit
detiene también ese nuevo lote, hasta que se resuelva por la vía explícita.

`SQLiteManagedRepository._queue_commit` contiene las comprobaciones del commit y
las comparten la acción propia y el lote. Esto aplica la excepción acotada a D026
que recoge D033.

## Enmienda y abandono

La migración `0011_phase_amendments` hace tres cambios:

- añade `phase_definitions`, con número, definición, hash, base documental,
  origen, motivo, identidad y fecha;
- añade `managed_phases.definition_number`;
- cambia el índice de fase abierta para excluir `CLOSED` y `ABANDONED`.

Las fases que ya existían reciben una versión 1 con origen `migrated`, sin motivo
ni identidad, porque no se infieren. Bajar de versión se rechaza si hay fases
abandonadas o enmendadas.

Al crear una fase se registra la versión 1 con origen `created`.

`amend` exige versión de fase, motivo y confirmación (HTTP). Tampoco puede haber
jobs pendientes en el checkout ni un check o cierre en curso. El código de la fase
no cambia, porque identifica sus runs. La enmienda debe modificar la definición.
Al aplicarla:

- se crea una versión nueva y la anterior queda intacta;
- `READY_TO_CLOSE` vuelve a `ACTIVE`;
- los lotes activos pasan a `INVALIDATED`;
- un documento nuevo se adopta con su hash actual y queda registrado en la
  operación `amend`;
- los documentos que ya existían conservan su base adoptada.

Un READY anterior no puede cerrar: el vínculo incluye el hash de la definición.

`abandon` lleva al estado terminal `ABANDONED`, con una operación `abandon`
auditada que guarda el motivo, la identidad, los lotes invalidados y las preguntas
abiertas. No edita documentos ni toca Git. Una fase abandonada rechaza tareas,
reanudaciones, commits, checks, preguntas y enmiendas, y deja el checkout libre
para crear otra fase. Su código no se puede reutilizar.

## Tags configurables

`ManagedProject.tag_kind` acepta `lightweight` (por defecto) o `annotated` y se
valida al arrancar. La autorización de cierre lo congela en su alcance y en la
operación. Con un tag anotado, la intención fija antes del efecto:

- el mensaje determinista, con fase y READY y sin el id de la operación;
- el nombre y el email del escritor Git;
- la fecha del reloj del repositorio;
- el `object` calculado con `hash-object -t tag` sin escribirlo.

El efecto escribe el objeto, comprueba que su id coincide con la intención y crea
la referencia por CAS con valor anterior nulo.

La conciliación compara el id del objeto, no solo el commit. Si un cierre
explícito posterior encuentra una intención incierta para el mismo ref, tipo,
commit y READY, reutiliza su mensaje, identidad y fecha, y obtiene el mismo
objeto. Un tag existente que apunte a otra cosa, incluido un tag ligero en el
mismo commit, termina en `FAILED` y nunca se mueve ni se sobrescribe. Los tags
ligeros se comportan igual que en H3.3.

## Reconciliación con agente

`submit_reconcile_task` (`POST /phases/{id}/reconcile-task`) crea un run de tarea
normal llamado `<fase>-RECONCILE-<n>` con un contrato determinista que fija el
servidor:

- `allowed_paths` limitado a los documentos de la fase;
- criterios tomados del último check REVISE;
- la primera selección explícita de ejecutor de la política;
- `prompt_template` con id y hash de `reconcile-phase` y el hash del texto
  renderizado.

El texto renderizado (definición, base, tareas y último check) es la instrucción
del ejecutor. `OfflineEngine.start(..., contract=...)` usa ese contrato ya
congelado, sin planificador, y comprueba que sea JSON canónico válido. La
plantilla se ha reescrito para que hable de ejecución bajo contrato, lo que cambia
su id base.

La tarea se revisa y se confirma por el flujo normal. Si escribe fuera de los
documentos, nunca es elegible. Solo puede haber una tarea abierta a la vez: en
curso, pendiente de commit o pendiente de adopción. Un intento fallido no bloquea
el siguiente. La adopción por hash (`reconcile`) exige que la tarea abierta esté
`COMMITTED`. Registra `source` (operación, run y commit) y marca la tarea como
`ADOPTED`. Si un documento está protegido por el perfil, la acción se rechaza.
Sin escritor Git no se ofrece y responde 409 `commit_writer_unavailable`.

## API y UI

Endpoints nuevos bajo la guardia gestionada:

- `POST /phases/{id}/amend`, que exige `confirmed`;
- `POST /phases/{id}/abandon`, que exige `confirmed`;
- `POST /phases/{id}/reconcile-task`, que exige `Idempotency-Key` y responde 202.

`PhaseBatchCreate` admite `chain_commits` y `text`; un lote desatendido sin
escritor Git devuelve 409. `PhaseRead` añade `definition_number`, `definitions` y
`tag_kind`, y las acciones `amend`, `abandon` y `reconcile_task`.
`ManagedProjectRead` añade `tag_kind`. OpenAPI y los tipos se han regenerado.

En la UI:

- el estado `Abandonada` y el historial de versiones de la definición;
- un formulario de enmienda que parte de la definición vigente, con motivo y
  confirmación;
- el abandono con motivo y confirmación;
- los lotes manual y desatendido, este con su plan congelado;
- el botón «Reconciliar con agente»;
- el tipo de tag en el texto del cierre.

Las confirmaciones se limpian cuando cambia la versión.
