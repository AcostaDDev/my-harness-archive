## `local-config-3`

```toml
format = "local-config-3"
[service] …            # igual que local-config-2
[git] …
[agents.reviewer] …    # igual que local-config-2
[agents.executor] …

[registration]
roots = ["/ruta/canónica/proyectos"]  # la UI solo registra carpetas bajo estas raíces
bootstrap_enabled = false             # techo: la UI solo puede activar bootstrap si es true

[compositions.web]                    # comandos con nombre, independientes del checkout
profile = "typescript-web"
authorize_profile_commands = true
executables = { node = "…", npm = "…" }
environment = { … }
# max_timeout_seconds, max_output_bytes, [[compositions.web.authorized]]

[[projects]]                          # opcional; nombra una composición en vez de llevar `commands`
id = "…"; root = "…"; repository_trusted = true; composition = "web"
# tag_kind, documents, permission_authority, bootstrap_enabled
[projects.policy] …
```

- Cada composición se valida al cargar (perfil conocido, ejecutables absolutos, comandos del perfil autorizados) con el
  directorio de estado como raíz provisional; el `CommandConfig` real se crea por proyecto.
- `local-config-1` y `-2` se leen igual y conservan su hash congelado (`local_config_sha256`, comprobado con la fórmula
  anterior). No admiten registrar desde la UI: `/registry` responde `available: false`.
- `LocalComposer` (`services/local_config.py`) guarda la autoridad compartida (agentes, Git, estado y composiciones) y
  compone proyectos del TOML al cargar y proyectos registrados en cualquier momento. Las fábricas de puertos y del
  escritor buscan la composición viva de cada checkout bajo un lock y comparan todas las versiones congeladas.
- `check-config` muestra `registration` (raíces, techo de bootstrap y composiciones con nombres de ejecutables y
  claves de entorno, nunca valores) y admite TOML sin `[[projects]]`.
- Plantilla `examples/local_config.example.toml` reescrita como `local-config-3`.

## Registro en SQLite (`0016_project_registry`)

- `registered_projects`: id, versión, estado (`ACTIVE`/`RETIRED`), raíz canónica, composición, perfil, fila canónica
  completa y su SHA-256, y la confianza confirmada (raíz, declaración y quién). Índice único de raíz entre activos.
- `registered_project_events`: una fila por versión, nunca reescrita: acción, fila, hash anterior y nuevo, hash de la
  vista previa confirmada, `actor()` (uid y cuenta del servicio, como el resto de auditorías), motivo y fecha.
- Baja lógica: la fila pasa a `RETIRED`, conserva su historial y su id queda reservado; la raíz queda libre para otro
  id. Los runs del checkout siguen legibles, sin proyecto ni acciones.
- El downgrade se niega si hay filas registradas.

## API

| Ruta | Efecto |
| --- | --- |
| `GET /api/managed/registry` | Opciones: raíces, techo de bootstrap, composiciones, proveedores y vocabulario de esfuerzos del ejecutor, ids reservados y del TOML, proyectos registrados con su disponibilidad |
| `GET /api/managed/registry/projects/{id}` | Fila, confianza, trabajos sin terminar e historial de auditoría |
| `POST /api/managed/registry/preview` | Sin efectos: fila resultante, cambios campo a campo, versiones que congelará cada job, trabajos sin terminar y `preview_sha256` |
| `POST /api/managed/registry/apply` | Confirma una vista previa: `change` + `preview_sha256` (+ `trust_root` en el alta, + motivo opcional) |

- `RegistryChangeInput` (`extra=forbid`, estricto) solo admite id, raíz (alta), composición nombrada, política D052,
  tag, documentos, bootstrap y techo de permisos. Ningún ejecutable, entorno ni argv se acepta por HTTP.
- `preview_sha256` liga acción, id, versión esperada, hash de la fila actual, estado, hash de la fila nueva y las
  versiones congeladas (incluido el hash de la composición del TOML). Si algo cambia entre la vista previa y la
  confirmación, `preview_changed`.
- La confianza es una confirmación aparte: el alta exige `trust_root` igual a la raíz canónica exacta.
- Repetir la misma confirmación ya aplicada devuelve el resultado con `replayed: true`, sin otra versión.
- Códigos: `root_not_absolute`, `root_not_canonical`, `root_missing`, `root_symlink` (cualquier componente),
  `root_not_directory`, `root_not_authorized`, `root_service_state` (contiene la SQLite o las migraciones), `invalid_id`
  (forma o reservado: `new`), `bootstrap_not_allowed`, `root_immutable` y `invalid_request` (422); `duplicate_id`
  (TOML, registrado o dado de baja), `root_taken` (igual o anidada con otro proyecto), `stale_version`,
  `preview_changed`, `trust_unconfirmed`, `pending_jobs`, `retired` y `registry_unavailable` (409).
- `ManagedProjectRead` añade `source` (`operator`/`registry`), `registry_version` y `bootstrap_enabled`.

## Runtime sin reinicio

- `ProjectRegistry` (`services/project_registry.py`) compone las filas activas al arrancar. Una fila que ya no compone
  (composición retirada del TOML, id ocupado por el TOML, otro formato) queda no disponible con su motivo; el servicio
  arranca igual.
- Alta y cambio instalan el proyecto en el runtime (`install`, copia nueva del mapa) y su composición en el
  `LocalComposer`; la baja los retira. Un cambio a la vez por proceso; la versión se comprueba en la transacción.
- El hash congelado (`local_config_sha256`) incluye la versión y el hash de la fila del registro, y `project_registry`
  aparece en las versiones. Cambiar o dar de baja con jobs `QUEUED`/`ACTIVE`/`RECOVERY_REQUIRED` o con el lock del
  checkout se rechaza en la misma transacción. Un job admitido entre el commit del registro y la instalación queda en
  cuarentena (`RECOVERY_REQUIRED`) antes de lanzar nada, como cualquier composición distinta de la congelada.
- La exclusión de un escritor por checkout no cambia: el lock sigue por raíz canónica, y el registro rechaza raíces
  iguales o anidadas con otro proyecto.

## UI

- `/projects/new` (enlace en la barra lateral y en Proyectos): id, raíz, composición (con perfil, nombres de
  ejecutables y claves de entorno), política del ejecutor con el vocabulario de su proveedor, tag, documentos v2,
  bootstrap (desactivado si el operador no lo autoriza) y techo de permisos JSON. «Revisar alta» muestra la vista
  previa; cualquier edición la invalida. La confirmación pide la casilla de revisión y, aparte, la de confianza en la
  raíz exacta. Al registrar lleva al resumen del proyecto, donde se encola la primera tarea.
- Ajustes de un proyecto registrado: versión, confianza, trabajos sin terminar, auditoría, «Cambiar el registro» con
  la misma vista previa y «Dar de baja» con confirmación. Los proyectos del TOML se marcan como del operador.
- Proyectos: columna Origen y aviso de proyectos registrados que no se componen con el TOML actual.
- `/projects/new` es una ruta propia; el servidor reserva el id `new`.

## Límites

- Un cambio de versión del registro invalida los jobs admitidos con la anterior, también el commit de un run ya
  aceptado: ese commit queda en cuarentena como con cualquier cambio del TOML. Conviene confirmar los commits
  pendientes antes de cambiar el registro.
- La sesión de la QA la inició el usuario: el clasificador de permisos denegó leer el archivo de clave.
- La raíz no cambia tras el alta; reactivar un id dado de baja no está soportado (se registra con otro id).
- Entre la comprobación de la raíz y su uso, la carpeta podría sustituirse por un enlace; el riesgo es el mismo que en
  los proyectos del TOML.
- Solo se admite el perfil `typescript-web` (el de las composiciones).
- El registro con bootstrap habilitado deja preparada la carpeta; la creación desde la UI es E4.
