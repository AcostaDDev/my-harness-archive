# H2.4 — Git y aceptación offline

Entrega: 2026-10-12. [Alcance original](NEXT_STEPS.md) conservado. Todo se verifica
con repositorios Git temporales, SQLite sintética y agentes falsos; sin proveedores,
CLI de agente, red, API/CLI/UI gestionadas ni cambios de configuración global.

## Frontera e integración

- `core/engine/commit.py` (biblioteca estándar): contrato de intención/resultado,
  puertos `CommitWriter`/`CommitJournal`, comprobación de aceptación vigente y
  orquestación `commit_accepted`. No lanza procesos ni conoce SQLite.
- `adapters/git.py`: `Git` (ejecutor con entorno explícito), `GitWorkspace`
  (captura completa + escritor de commit idempotente) y `GitWorktrees`.
- `storage/managed.py` + migración `0006_git_commits`: tabla `managed_commits` y
  métodos `submit_commit`, `commit_intent`, `commit_result`, `commit_record`.
- `services/managed.py`: el supervisor acepta `commit_factory` y procesa jobs de
  acción `commit` bajo el mismo lease, heartbeat y lock de checkout que el resto.
- `ContentEvidence` gana `provenance_json` (opcional). `SyntheticWorkspace` sigue
  sin procedencia y **no puede** respaldar un commit.

El camino es explícito y por inyección, igual que H2.3: no hay endpoint, comando
CLI ni autoarranque que cree worktrees o commits.

## Evidencia Git: qué se captura

`GitWorkspace.capture(context)` calcula, sin tocar HEAD, índice real ni archivos:

1. `HEAD` (base) y su árbol.
2. `index_tree`: árbol del índice real (copia temporal, `write-tree`). Un índice
   con conflictos falla; nunca se resuelve implícitamente.
3. `worktree_tree`: árbol de lo que `git add -A` registraría ahora, calculado sobre
   otra copia temporal del índice. Incluye staged, no staged, nuevos y borrados,
   cambios de modo y enlaces simbólicos como contenido.
4. Rutas cambiadas y parche completo (`diff-tree -p --binary --full-index`) entre
   base y `worktree_tree`, más listas de rutas staged/untracked/borradas.

`fingerprint = sha256({format, base_revision, worktree_tree, index_tree})`. El
estado de staging forma parte de lo revisado: cambiar solo el índice tras la
revisión invalida la aceptación y el commit nunca descarta staging no visto.
`provenance_json` conserva los identificadores de árbol, listas de rutas, SHA-256
y tamaño exacto del parche y versión de Git. El parche no se trunca: más de
4 MiB (configurable) detiene con error de evidencia, igual que submódulos/gitlinks,
rutas no UTF-8, raíz que no es el nivel superior del checkout o HEAD sin commits.

Los archivos ignorados quedan fuera de evidencia y de commit (ni se revisan ni se
tocan). Solo se escriben objetos Git sueltos (blobs/árboles) en el repositorio.

## Worktree por tarea

`GitWorktrees.prepare(repositorio, destino, branch=..., base=...)`:

- Destino absoluto, padre existente y fuera del checkout de origen. Rama validada.
- Idempotente: un worktree registrado con la misma rama se devuelve sin limpiar,
  reiniciar ni tocar sus modificaciones. Ruta existente no registrada, rama ya
  existente en otro sitio o rama distinta en la ruta se rechazan sin sobrescribir.
- No hay `remove`/`clean`/`reset`: el checkout principal queda byte a byte igual
  (estado, índice y contenido comprobados con cambios staged/unstaged/untracked).
- La raíz del worktree es la raíz canónica de lock: tareas en worktrees distintos
  avanzan a la vez; una segunda acción sobre el mismo worktree espera.

Un worktree separa trabajo Git; no es un sandbox de seguridad.

## Commit acotado e idempotente

Gate (`prepare_commit`, sin efectos): run `acceptance_ready` con aceptación
elegible, procedencia Git válida y `assess_acceptance` sobre una captura nueva.
Cualquier diferencia (contenido, staging, base) → `invalidated` sin intención; el
run pasa a STOPPED en etapa `commit` y el flujo normal de revalidar/revisar de nuevo
produce evidencia nueva.

Intención (persistida antes del efecto): `operation_id`, base, fingerprint revisado,
árbol revisado, árbol de índice revisado, rutas, actualizaciones mecánicas, árbol
esperado, **identificador de commit esperado**, mensaje, identidad y marca de
tiempo. El commit se construye a mano (`tree`/`parent`/`author`/`committer`) y su id
se calcula con `hash-object` sin escribir: es determinista. Mensaje con trailers
`Harness-Operation`, `Harness-Run`, `Harness-Reviewed-Fingerprint`,
`Harness-Reviewed-Tree` y `Harness-Mechanical`.

Ejecución (`GitWorkspace.execute`), siempre reconciliando primero:

1. Si HEAD es el commit esperado o lo tiene como ancestro, se verifica el contenido
   del objeto byte a byte → `reconciled`; nunca se crea otro commit.
2. HEAD movido sin commit propio: si el objeto esperado no existe → `invalidated`;
   si existe pero no es alcanzable → `CommitUncertain` (recuperación manual).
3. HEAD == base: nueva captura; fingerprint distinto → `invalidated`, sin commit.
   Se escribe el objeto y se mueve la referencia con compare-and-swap
   (`update-ref HEAD <nuevo> <base>`). Un CAS fallido se reobserva.
4. Tras mover la referencia, el índice real solo se sustituye por el árbol del
   commit si sigue igual al índice revisado (`refreshed`); si ya coincide
   (`already_current`) o contiene staging posterior se deja intacto (`left_untouched`).

El commit se crea desde identificadores de árbol, no con `git add -A`/`git commit`:
sin hooks, sin firma, sin filtros globales. Una edición posterior a la revisión
nunca entra en el commit; queda como cambio sin confirmar sobre el nuevo HEAD.

**Actualizaciones mecánicas** (`MechanicalUpdate`: ruta, texto UTF-8, motivo) se
declaran en la solicitud, se validan antes de cualquier efecto (ruta segura, no
sensible, sin solape con lo revisado, sin duplicados, nunca `.git`), se fijan en
la intención con su hash de árbol y solo entonces se escriben en el worktree
(atómicamente, todos los destinos validados antes). El commit contiene exactamente
árbol revisado + estas actualizaciones; una caída tras escribirlas se reanuda con el
mismo árbol sellado.

## Persistencia

Migración explícita `0006_git_commits` (`alembic check` correcto): `managed_commits`
con índice único parcial (como máximo una operación `INTENT`/`COMMITTED` por run).
`commit_intent` y `commit_result` son transacciones cortas con evento
(`commit_intent`, `commit_recorded`, `commit_invalidated`). Estados de run
`COMMITTING` y `COMMITTED`; `COMMITTED` solo significa commit de checkpoint creado
en el worktree: no es integración en rama destino ni cierre. Un run con operación
pendiente o registrada no se puede reanudar con `resume`; con intención pendiente,
`submit_commit` solo concilia (mecánicas distintas → conflicto). El downgrade a
`0005` elimina `managed_commits` y conserva los runs. Historial con procedencia usa
formato 3; sin ella conserva exactamente los formatos 1/2.

## Caídas cubiertas (inyectadas en pruebas)

| Punto | Estado Git | Recuperación |
|---|---|---|
| Tras la intención, antes del objeto | HEAD=base, sin objeto | crea el commit esperado una vez |
| Objeto escrito, antes de mover la ref | HEAD=base, objeto existe | mueve la ref al mismo id |
| Ref movida, antes de guardar resultado | HEAD=esperado | `reconciled`, sin segundo commit |
| Ref movida y usuario siguió trabajando | HEAD descendiente | `reconciled`, historial/ediciones intactos |
| Tras escribir mecánicas | worktree = árbol sellado | continúa con el mismo árbol |
| HEAD movido, objeto inexistente | otra base | `invalidated`, revalidar |
| HEAD movido, objeto existente inalcanzable | ambiguo | cuarentena + evidencia, lock retenido |
| Contenido cambiado tras la intención | HEAD=base | `invalidated`, sin commit |

Tras una caída real el job queda `RECOVERY_REQUIRED` con el lock retenido (H2.2);
`confirm_stopped` explícito y un nuevo `submit_commit` concilian la intención.

## Límites

- macOS actual con Git 2.50.1 (Apple Git-155); Linux/Windows y repositorios
  SHA-256 no probados. Un solo escritor cooperativo por base; escritores Git
  externos solo se detectan por comparación (fingerprint/CAS).
- Entre la comprobación del contenido y el CAS hay una ventana corta; una edición
  en ella no entra en el commit y queda como cambio posterior (no se pierde).
- Configuración global/de sistema y hooks desactivados; la configuración local
  del repositorio (p. ej. filtros `clean` definidos localmente) sí se respeta.
- Objetos sueltos no referenciados pueden retirarse con `git gc` tras su caducidad;
  la evidencia duradera es el parche y su hash guardados en SQLite.
- No hay integración en rama destino, push, limpieza/retirada de worktrees,
  entradas API/CLI/UI, abandono manual de una intención ambigua ni formateador.
  `commit_factory` debe validar la versión de evidencia congelada; el repositorio
  solo la registra.
