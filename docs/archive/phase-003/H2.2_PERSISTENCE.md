## Persistencia y snapshots

Crear un run guarda contexto canónico/perfil/política, versiones declaradas,
texto de planificación, identidades de fase/tarea, presupuesto y job. Cada
intento guarda identidad nueva, número por run, rol, selección, prompt efectivo,
contrato y contexto exactos, versiones, intención previa y resultado posterior.
El planificador conserva `task_json=null` hasta producir un contrato válido;
el contrato resultante queda congelado antes de invocar al ejecutor.

Las versiones de componentes son obligatorias en la solicitud; una versión
desconocida se registra como null. Son metadatos declarados, no versiones CLI
observadas: la factory recibe esa selección congelada y debe rechazar versiones
que no tenga. No hay sustitución de proveedor/modelo ni versión en recuperación.

Historial acumulado, preparación, validaciones, evidencia sintética, reviews,
stops y elegibilidad se serializan como valores inmutables. El repositorio
rechaza cambios de contrato/contexto, eliminación de historial y reemplazo de
resultados o reviews registrados. Los resultados de comando se registran también
como eventos con identidad y su intención previa; si una validación cae antes
de terminar el ciclo, su evidencia parcial queda en el feed de comandos.

Cada checkpoint guarda estado/historial/resultados y su evento en la misma
transacción. Eventos con secuencia única creciente por run, timestamps UTC y
lectura paginada. La versión del recurso coincide con esa secuencia y permite
rechazar acciones de recuperación basadas en una lectura obsoleta. No es event
sourcing: el historial actual conserva sus intentos/ciclos anteriores.

El estado operativo muestra PREPARING/PLANNING/EXECUTING/VALIDATING/REVIEWING
mientras el job está activo. Al terminar conserva STOPPED/BLOCKED/REVISION_LIMIT
o ACCEPTANCE_READY. DONE significa que la acción del job acabó; no certifica
aceptación, commit o cierre. ACCEPTANCE_READY mantiene el gate offline H2.1.

## Cola, idempotencia y propiedad

`submit(..., key=...)` identifica una operación mediante una clave persistida
única. Solicitudes idénticas devuelven el mismo job incluso después de acabar;
reutilizar la clave con contenido distinto produce conflicto. El llamante debe
reutilizar la clave para la misma acción; una clave nueva expresa otra operación.
Revalidar/reintentar requiere run, versión esperada y clave propia. Solo se
permite una acción pendiente por run y no se altera su contexto original.

Política de cola: FIFO por ID entre jobs elegibles, con un escritor por raíz
canónica. Un job bloqueado no impide progreso en otra raíz; llamadas explícitas
concurrentes a `run_once` pueden ejecutar checkouts distintos. No hay pool ni
despacho automático. Rutas con `.`/`..` o alias de enlace que resuelven a la misma
raíz comparten el bloqueo. SQLite gestionada debe quedar fuera del checkout.

La primera operación de cada transacción escritora adquiere el lock SQLite
antes de leer decisiones de cola. Claim, token de propietario nuevo, lease UTC,
heartbeat, bloqueo del checkout, estado y evento se confirman juntos. Después
se cierra la transacción. El motor y sus puertos no mantienen sesiones SQL.
Un hilo por `run_once` renueva el heartbeat cada tercio del lease; cada nueva
escritura comprueba token, vigencia y bloqueo. La conexión de heartbeat también
usa transacciones cortas. No se renueva una propiedad ya vencida.

## Caídas y recuperación

| Situación | Resultado persistido y acción posterior |
|---|---|
| Doble solicitud/claim concurrente | Un único job/propietario y una sola ejecución falsa |
| Fallo al encolar o reclamar | Rollback de estado, job, lock y evento; no se ejecuta un puerto |
| Fallo al guardar intención | No se hace la llamada; el supervisor deja recuperación pendiente |
| Error/terminal ausente/salida inválida del agente | Intento y resultado conservados; STOPPED, sin fallback ni review adicional |
| Caída durante efecto o fallo al guardar su resultado | Intención con resultado desconocido; se conservan archivos y bloqueo |
| Fallo al confirmar fin | Historial anterior conservado, job en recuperación; no se repite el flujo |
| Lease vencido o heartbeat fallido | RECOVERY_REQUIRED; no libera raíz ni reencola |
| Confirmación explícita del escritor detenido | INTERRUPTED, intento pendiente marcado de resultado desconocido y lock liberado atómicamente |
| Recuperación de trabajo | Nueva acción explícita: revalidar o reintentar, con sesión nueva y presupuesto original |

`recover_expired` se ejecuta antes de reclamar y puede invocarse al iniciar o
periódicamente. Nunca considera un lease vencido prueba de muerte. La operación
`confirm_stopped` exige el job/token exactos, versión esperada y motivo/evidencia
de conciliación; **el llamante debe haber descartado al escritor anterior**.
Esta operación registra esa confirmación, no detecta ni mata procesos reales.
En las pruebas se confirma después de salir de la llamada falsa y unir su hilo.

Los intentos pendientes se incorporan al historial como interrumpidos, sin exit
code ni éxito inventados. Una corrección iniciada reserva presupuesto aunque
su resultado no se haya guardado. Revalidar conserva el presupuesto y trabajo;
reintentar consume otra corrección y exige una identidad nueva. Sin contrato
válido no hay resume: una nueva planificación requiere otro run explícito.
No se reanuda conversación ni se reproduce un efecto de resultado incierto.

## Límites

Exclusión cooperativa dentro de una única base SQLite local, sobre raíces
canónicas. No impide escritores externos, otra base, aliases por montaje que
no resuelvan a la misma ruta ni checkouts que se solapen por anidación. Requiere
la futura transición H2.5 antes de activar proyectos legacy gestionados.
Tiempos de lease usan el reloj UTC local; no son prueba de liveness. No hay
garantía de ejecución externa exactamente una vez.

No hay procesos CLI/cancelación/grupos/smoke H2.3, captura Git completa/worktrees/
commit H2.4, UI gestionada, migración de proyectos, chat, permisos interactivos
ni blobs pesados/retención. La persistencia actual usa resultados sintéticos
pequeños. No se mide rendimiento bajo carga ni se prueban otros sistemas.
API/UI mantienen el recorrido H0/H1. No se arrancaron servicios ni proveedores,
harness de desarrollo, agentes, sesiones externas o configuración global.
Se conservan los avisos conocidos de uv sobre el entorno externo ignorado y
de Starlette/HTTPX. H2.3 queda pendiente, sin iniciar.
